# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A curated music discovery site, India/Bollywood-focused: browse curated "hits" playlists, a Trending chart, Recently Played, or search any song, played through an embedded **YouTube IFrame Player API**. It does not extract/download/rip audio anywhere (client or server) — that's intentionally out of scope (copyright/ToS reasons, see README). Playlists ("Liked Songs" + custom ones) live in `localStorage` by default, or sync server-side once an optional account system is enabled; playback always streams live from YouTube. Also shippable as a sideloadable Android APK (a Trusted Web Activity wrapper around the PWA — see "Android packaging" below).

Two workspaces, both plain JS (no TypeScript):
- `server/` — Express API (CommonJS): search proxy + cached curated category playlists + optional Postgres-backed accounts, backed by the YouTube Data API v3.
- `client/` — React 18 + Vite (ESM) frontend: UI, player, library, PWA.

## Commands

From the project root (npm workspaces — `client` and `server`):

```powershell
npm install          # installs both workspaces
npm run dev           # runs server (nodemon, :5000) + client (Vite, :5173) concurrently
npm run build          # builds client only -> client/dist
npm start             # node server/index.js (production-style: one process serves API + built client/dist)
```

Per-workspace, when you only need one side:

```powershell
npm run dev --workspace=server   # or: cd server; npm run dev  (nodemon)
npm run dev --workspace=client   # or: cd client; npm run dev  (vite)
```

There is no lint or test setup in this repo (no `lint`/`test` scripts, no test files) — don't assume one exists.

Required env var to run the server at all: `server/.env` must have `YOUTUBE_API_KEY` (copy from `server/.env.example`); `server/index.js` exits at startup if it's missing. Other server env vars (`PORT`, `CATEGORY_CACHE_TTL_HOURS`, `SEARCH_CACHE_TTL_MINUTES`, `TRENDING_REGION`, `TRENDING_CACHE_TTL_HOURS`, `CLIENT_ORIGIN`) are documented in the README. `DATABASE_URL` + `JWT_SECRET` are optional — see "Accounts" below. Client-side, `VITE_API_BASE_URL` points the built frontend at a separately-hosted API (see Deployment below) — in dev, Vite proxies `/api` to `localhost:5000` instead (`client/vite.config.js`).

## Architecture

### Server: routes → cacheService → youtubeService

`server/index.js` mounts `/api/{search,categories,related,artists,track,trending,auth,playlists,recent}` routes and, in production, also serves the built `client/dist` as static files with an SPA catch-all fallback — one process serves everything (`npm start`). In split deployments (see Deployment) the server only serves the API. The static-file middleware explicitly sets `dotfiles: "allow"` — Express's default (`ignore`) would otherwise silently swallow `/.well-known/*` (needed for Android app-link verification, see "Android packaging") into the SPA catch-all's `index.html`.

Every route (`server/routes/*.js`) delegates to `server/services/cacheService.js`, which is the only thing that talks to `server/services/youtubeService.js` (the raw YouTube Data API v3 client). Never call `youtubeService` directly from a route — the caching layer is what keeps quota usage sane (YouTube's free tier is 10,000 units/day; one `search.list` call costs 100, a `videos.list` call costs 1).

`cacheService.js` runs several independent `node-cache` instances with different TTLs/purposes, most disk-backed via a shared `makeDiskBackedCache({file, cache})` helper (`.persist()`/`.load()`, versioned via `DISK_FORMAT_VERSION` so an incompatible on-disk shape is discarded rather than misread) so a restart (dev reload, Render cold-start/redeploy) reuses prior fetches instead of re-spending quota:
- `categoryCache` — curated homepage playlists (long TTL, from `CATEGORY_CACHE_TTL_HOURS`). **Deliberately not** eagerly refreshed for every category on boot — only categories a visitor actually opens get fetched (lazy, on cache-miss); see the `startScheduledRefresh` comment for why (avoids burning ~1,000 units on every free-tier cold start). Every track gets tagged with `categoryId` (the category it was fetched for) — this is what the related-tracks pool sampler groups by.
- `trendingCache` — YouTube's `mostPopular` chart (`youtubeService.getTrendingVideos`), region from `TRENDING_REGION` (default `IN`), TTL from `TRENDING_CACHE_TTL_HOURS`. Only 1 quota unit per refresh (`videos.list` with `chart=mostPopular`, snippet+contentDetails together — no separate duration lookup needed, unlike search results).
- `searchCache`, `relatedCache`, `artistTracksCache`, `artistInfoCache`, `trackInfoCache` — shorter-lived, bounded by `maxKeys`, keyed by query/category/artist/videoId/channelId as appropriate. `trackInfoCache` is the one exception left memory-only (cheap to rebuild, low value to persist).

**Related-tracks / autoplay-radio (`cacheService.getRelatedTracks`, `server/services/relatedPool.js`)**: this used to search YouTube fresh on every single autoplay refill (100 units, guaranteed cache-miss since it was keyed by the just-played video's id) and only ever returned more songs from the same artist. It now samples from tracks the server already paid quota for instead: `relatedPool.samplePool()` pulls from the current category's cached tracks when the source track's `categoryId` is known (real genre match, cross-artist), or from every cached category **plus `trendingCache`** when it isn't (search/artist-page origin) — trending is included specifically because it's the one thing guaranteed to be warm on a fresh deploy or for a listener who never clicks a category tile, whereas category caches only fill in once someone actually browses one. Only when that local pool has fewer than `POOL_MIN_UNSEEN` (6) unseen tracks does it fall back to a live search, keyed by **category/artist** (not by source videoId, so it's reusable across every track that maps to it) using `server/utils/deriveArtist.js`'s heuristic (`<Artist> - Topic` channels, `Artist - Title` convention, Bollywood-style credit lists) only as the last resort when no category is known.

Selection *within* that sampled pool used to be a flat Fisher-Yates shuffle — same-genre when `categoryId` was known, but otherwise arbitrary about which specific song played next, with zero artist-affinity signal. `samplePool` now ranks candidates into 4 tiers (`tierOf`: same category+artist > same category > same artist > catch-all) built from the only two real "vibe" signals this YouTube-sourced schema actually has (`categoryId`, `channelId` — there's no genre/mood/BPM/tags/album/year field to score against). Same-artist tracks (tiers A+C) are capped at `SAME_ARTIST_CAP` (3 of the 12 returned) so an artist with deep catalog coverage in the cache can't crowd out the pool's original cross-artist variety goal; each tier is still internally shuffled so repeated refills for the same source track don't feel stale. The source track's `channelId` travels client → `api.js` → `GET /api/related/:videoId?channelId=` → `cacheService.getRelatedTracks` → `samplePool` as an optional param, mirroring the existing `categoryId`/`exclude` convention at each layer.

Curated category search queries (`server/config/categories.js`) explicitly say "bollywood"/"hindi", and category + related-fallback searches pass `regionCode: "IN"`, `relevanceLanguage: "hi"` to `youtubeService.searchVideos` — without this YouTube's generic query terms return globally-popular (often Western) results, not what a Bollywood-branded site wants for its curated playlists. Free-text `/api/search` deliberately has none of this bias — it's meant to find anything.

`server/utils/apiError.js` centralizes YouTube quota-exceeded detection (429/403 with a quota-ish reason) so routes can return a distinct `quota_exceeded` message instead of a generic 500.

### Accounts (optional, Postgres-backed)

Fully gated by `DATABASE_URL` being set (`server/db/index.js`'s `isDbConfigured()`) — unset, `/api/{auth,playlists,recent,player-state}` all return `503 accounts_disabled` and the app behaves exactly as guest-only/localStorage-only. When set, `runMigrations()` creates `users`/`playlists`/`recent_plays`/`player_state` idempotently on boot (plain `CREATE TABLE IF NOT EXISTS`, no migration framework). Auth is a JWT in an httpOnly cookie (`server/middleware/requireAuth.js`, sliding 30-day expiry, reissued on every authenticated request); cookie `sameSite`/`secure` flags are `NODE_ENV`-conditional since prod (split Netlify+Render deployments) needs `SameSite=None; Secure` while local dev needs `Lax`/insecure. Playlist track add/remove (`server/routes/playlists.js`) use atomic single-statement `jsonb ||` / `jsonb_agg` filter SQL rather than read-modify-write, to avoid races.

### Client: single persistent player via context

`client/src/context/PlayerContext.jsx` is the center of the app. It's mounted once, **above** the router in `App.jsx`, so neither of its two `YT.Player` instances is ever torn down on navigation — that's the mechanism that lets playback survive page changes. It wraps two instances of `client/src/hooks/useYouTubePlayer.js` (one per player "slot"), which lazily injects the YouTube IFrame API script exactly once (shared across both) and exposes each player instance via a ref (not React state, since `YT.Player` mutates itself internally). `PlayerContext` also owns: the play queue/autoplay-radio logic (calls `/api/related` with the current track's `categoryId`/`channelId` and the whole current queue as `excludeIds` when it runs out — see server-side pool sampler above), the "Up Next" queue panel's reorder/remove/jump-to-track actions (`reorderQueue`/`removeFromQueue`/`playFromQueue`, scoped to indices after `currentIndex` — already-played history isn't touched), local + server recently-played recording (`recordPlay`/`recordServerPlay`, the latter fire-and-forget and silently ignored on 401/503 — deliberately never imports `AuthContext`, staying decoupled), Media Session API metadata/handlers (lock-screen controls), and a Screen Wake Lock (keeps the screen from idle-timing-out during playback — see README for the platform limits on this, it can't survive an intentional screen lock on iOS/Android because YouTube's iframe gets suspended).

It also persists queue/track/position/volume/autoplay across a refresh (`utils/playerState.js` for the localStorage side, `GET`/`PUT /api/player-state` for the server side), following the exact same decoupled fire-and-forget pattern as `recordServerPlay` above so it never needs to import `AuthContext` either — a write always goes to both localStorage and (best-effort) the server, and restore-on-mount tries the server first, falling back to localStorage on a 401/503. Writes are throttled (every `PERSIST_INTERVAL_MS` while playing, plus immediately on pause/track-change/tab-hidden/`beforeunload`) rather than on every position tick. Restoring cues the saved track **paused**, not playing — deliberately, since unmuted autoplay without a fresh user gesture is unreliable/blocked in most browsers, and starting audio the instant the page loads would be jarring even on browsers that do allow it.

**Crossfade (`beginTransition`)**: track changes used to be a hard cut (`loadVideoById` on the one player, stopping the old track instantly). There's no Web Audio access to crossfade with (cross-origin iframe, see below), so the two players take turns being "active" (audible) vs "standby": a few seconds before a track naturally ends (`CROSSFADE_TRIGGER_SECONDS`), or immediately on a manual Next/Previous/queue-jump, the standby player silently preloads and starts the next track, and a `setInterval` ramps volume from the active player over to it via each player's own `setVolume()`, then flips which slot is "active". Natural end-of-track gets the full `CROSSFADE_DURATION_AUTO_MS` musical fade; manual actions get a quick `CROSSFADE_DURATION_MANUAL_MS` fade instead of a click. The queue is proactively refilled (`REFILL_TRIGGER_SECONDS`, well before the crossfade trigger) so a next track already exists when the fade needs one, rather than racing a network call. `activeSlotRef`/`isTransitioningRef` are refs, not state, since callbacks/intervals read them synchronously; `activeSlot` is mirrored into state too, but *only* to drive which of the two hidden players shows in the small corner video preview — everything else derives from `queue`/`currentIndex`/`isPlaying`/etc. as before. If the natural-end timer is ever missed (e.g. a backgrounded tab throttles `setInterval`), the `ENDED` event falls back to an instant (0ms) transition rather than just stopping.

One non-obvious gotcha baked into the render at the bottom: the `is-active` class that controls which player's iframe is visible lives on a **wrapper div that React fully owns**, never on the `id={...}` div YouTube's IFrame API targets directly. The API replaces that div with an iframe at construction time and copies whatever class it had *at that moment* onto the iframe — a one-time copy, not a live binding. Put `className` directly on that div and every later re-render silently updates a phantom node no longer in the live DOM, while the real iframe's class stays frozen forever (this cost real debugging time to track down - the crossfade audio/state worked fine, only the visual "which player is active" indicator silently never updated).

`client/src/components/QueuePanel/QueuePanel.jsx` is a slide-in drawer (toggled from a button in `PlayerBar.jsx`) showing the current track + upcoming queue, drag-to-reorder via framer-motion's `Reorder` (no extra dependency).

`client/src/context/AuthContext.jsx` (optional accounts, parallel to `PlayerContext`, not cross-imported by it) tracks `user`/`accountsEnabled` via `GET /api/auth/me` on mount — a `503` means the deployment has no `DATABASE_URL` and all login UI stays hidden; a `401` means guest-with-accounts-available, showing a Log in link in `Header.jsx`. On successful login/signup it also checks `localStorage` for pre-existing guest playlists (`hasImportableLocalData`/`hasBeenPromptedForImport` in `utils/playlists.js`) and, once per browser, surfaces `ImportPlaylistsPrompt.jsx` to offer merging them into the new account via `importLocalPlaylistsToAccount` — declining never deletes the local copy, it's just left behind as an orphaned backup.

`client/src/services/api.js` is a thin axios wrapper around the `/api/*` routes (`withCredentials: true` for the auth cookie); `baseURL` comes from `VITE_API_BASE_URL` when set (split deployment) or defaults to the Vite dev proxy.

`client/src/utils/playlists.js` is **dual-mode**: guest mode (default) manages playlists — including the built-in "Liked Songs", id `"liked"`, which can't be renamed/deleted — directly in `localStorage`, byte-identical to how the app worked before accounts existed. Account mode (flipped via `setPlaylistsAuthState(userId)`, called from `AuthContext`) mirrors server state in an in-memory `cachedPlaylists` with **optimistic** mutations (mutate + notify synchronously, fire the API call in the background, roll back on failure) so every existing call site keeps working unmodified despite now being backed by a network call. A freshly-created playlist gets a temporary `tmp_...` id immediately (so "create then add a track to it" in the same click, e.g. `AddToPlaylistMenu`'s new-playlist form, keeps working) — mutations against a still-pending temp id chain onto that create's promise and re-target the real id once the server responds, rather than racing it. `isPlaylistsLoading()` (true only in account mode before the first `refreshPlaylists()` resolves) guards `PlaylistDetail.jsx`/`Playlists.jsx` against a false "not found"/empty flash right after login. Either mode: state lives outside React, so a manual pub-sub (`subscribeToPlaylistChanges`) keeps components in different parts of the tree (e.g. `TrackCard` and `PlayerBar`) in sync when a track is liked/unliked from either place.

Routing (`App.jsx`, react-router-dom): `/`, `/category/:id`, `/search`, `/library`, `/playlist/:id`, `/artist/:channelId`, `/track/:videoId`, `/login`, `/signup` — the first set of dynamic routes back the app's shareable links (artist pages, single-track pages); page transitions wrap every route in `client/src/components/PageTransition/PageTransition.jsx` via `AnimatePresence mode="wait"`.

PWA support is configured in `client/vite.config.js` via `vite-plugin-pwa` (manifest, service worker, `devOptions.enabled: true` so the SW also generates under `npm run dev`, not just prod builds). Decorative `isPlaying`-driven animation (spin/glow ring on `AlbumArt.jsx`, equalizer bars, gradient accent strip on `PlayerBar.jsx`) is CSS/framer-motion only — the player is a cross-origin YouTube iframe with no Web Audio access, so none of it reflects real audio data, by design (see README).

### Android packaging

The PWA above is also shipped as a sideloadable Android APK — a Trusted Web Activity (TWA) generated externally via PWABuilder (pwabuilder.com), not part of this repo's build. The one piece that *is* repo-side: `client/public/.well-known/assetlinks.json` (Digital Asset Links, proves the APK owns this domain so Android opens it chromeless instead of showing a browser address bar) — see the `dotfiles: "allow"` note above for why that path needed a server-side fix to actually be served.

## Deployment

Two supported shapes:
- **Split**: frontend → Netlify (`netlify.toml`), backend → Render (`render.yaml`), because Netlify can't run the long-lived Express process the in-memory/disk cache depends on. Set `VITE_API_BASE_URL` (Netlify build env) to the Render URL + `/api`, and lock down `CLIENT_ORIGIN` (Render env) to the Netlify URL once accounts/cookies are involved (a credentialed cross-origin request needs an explicit allowlist, not "allow all").
- **Single-service**: Render alone, build command `npm install && npm run build` (not just `npm install` — the build step is what actually produces `client/dist` for the server to serve; `render.yaml`'s `buildCommand` reflects this, but note Render services created manually before `render.yaml` existed won't pick up changes to that file automatically, it has to be edited in the Render dashboard directly for those). No `VITE_API_BASE_URL`/`CLIENT_ORIGIN` cross-origin concerns since frontend and API share an origin.

If accounts are enabled, also set `DATABASE_URL` (Postgres — Render's own disk is ephemeral, wiped on every redeploy, so a managed Postgres like Neon/Supabase is required) and `JWT_SECRET` on the backend service; see README's "Accounts (optional)" section for how to get a connection string and generate a secret.

Locally, `npm run build && npm start` runs the single-process production mode instead of split (no Netlify needed for local testing).
